## 1. Engine callback API-key check can be skipped with a percent-encoded unreserved character in the callback path

Fingerprint: `SEC-AUDIT-001:callback-api-key-filter-encoded-path-bypass`

ApiKeyAuthenticationFilter enforces the X-API-Key header only when the raw, undecoded request URI starts with the literal prefix /api/v1/solutions/callbacks/. The same path is permitAll in SecurityConfig, so this filter is the only authentication on the Engine callbacks. Source review of the resolved dependency versions (Spring Boot 3.5.7 parent -> Spring Security 6.5.6, Spring Framework 6.2.12, Tomcat 10.1.48 in the local Maven repository) indicates that a raw URI that percent-encodes an ordinary letter, for example /api/v1/solutions/%63allbacks/complete or /api/v1/solutions/callback%73/failed, (a) is not rejected by the default StrictHttpFirewall, whose encoded blocklist only contains %25, %2e/%2E, %2f, %5c, %3b, %00, %0a, %0d (and their decoded forms) and whose normalization check only looks for dot segments; (b) does not start with the literal prefix, so the filter calls filterChain.doFilter without checking the key; (c) is matched by Spring MVC PathPattern matching, which decodes each segment (DefaultPathContainer.decodeAndParsePathSegment -> valueToMatch, compared by LiteralPathElement), so it maps to OptimizationCallbackController; and (d) is matched by the requestMatchers("/api/v1/solutions/callbacks/**") permitAll rule, which in Security 6.5.6 without a PathPatternRequestMatcher.Builder bean resolves to MvcRequestMatcher (HandlerMappingIntrospector, same decoded matching as MVC) or AntPathRequestMatcher on the container-decoded servletPath. Semicolon path parameters, encoded slash or period, double slash, backslash and dot segments are blocked by the default firewall; case variants do not match because PathPattern and the security matcher are case-sensitive. The application does not customize the firewall, UrlPathHelper, path matching or the filter registration (no HttpFirewall, PathMatchConfigurer, FilterRegistrationBean or matching-strategy setting found). Impact if reachable: an anonymous caller can POST forged complete/failed/cancelled/progress callbacks for any job. OptimizationCallbackService looks the job up with jobRepository.findById(callback.getJobId()) only (IDENTITY-generated, guessable Long ids), with no engine or job token, so it can mark another branch's PROCESSING job FAILED or CANCELLED, or ingest an attacker-chosen solution; saveSolution loads orders with orderRepository.findAllById(orderIds) without a branch filter and bulk-transitions their status (ON_ROUTE / UNASSIGNED), which suggests a forged completion could also change other branches' orders (cross-tenant write, not traced to completion in this review). Not observed at runtime: this is a source-only conclusion.

**Claimed root cause:** The API-key gate is decided by a string prefix check on HttpServletRequest.getRequestURI(), which is the raw, undecoded URI, while Spring Security authorization (permitAll) and Spring MVC handler mapping both operate on the decoded path; the components therefore disagree on which requests are callback requests, and the permitAll rule leaves no second line of defense.

## 2. Engine completion callback materializes and re-statuses orders and vehicles of other branches into a job's solution

Fingerprint: `SEC-AUDIT-001:callback-cross-branch-materialization`

OptimizationCallbackService.handleCompletion loads the target job by the callback's job_id only, then resolves every order_id and vehicle_id named in the callback payload with global findAllById calls and builds Route, RouteStop and UnassignedOrder rows that link those entities into a Solution owned by the job's branch. No comparison between the loaded orders/vehicles' branch and job.getBranch() exists anywhere on this path, and OrderStatusTransitionService.bulkTransition updates the named orders with an ID-only UPDATE. The Entry submit path (OptimizationJobService.validateAndLoadOrders/validateAndLoadVehicles) does enforce branch ownership, so the honest Entry->Engine->Entry loop echoes only branch-valid IDs; the gap is exploitable when callback content is not derived from that validated submission. Source shows such a lower-trust source: the Engine's POST /api/v1/optimization accepts an arbitrary job_id and caller-supplied orders/vehicles with no authentication (SEC-010, OPEN), solves them and then delivers the completion callback to the fixed Entry URL signed with the shared X-API-Key. A host that can reach the Engine port (or anyone holding the engine.api.key value, which is in git history per SEC-001) can therefore make Entry attach branch A's orders (customer name, phone, address, coordinates) and vehicles to branch B's PROCESSING or FAILED job, exposing them through branch B's solution views and moving branch A's SCHEDULED orders to ON_ROUTE/UNASSIGNED. Whether the Engine port and the callback path are reachable by such a party is a deployment fact not established by source.

**Claimed root cause:** The completion callback treats the payload's order and vehicle IDs as trusted and resolves them with unscoped repository lookups (orderRepository.findAllById, vehicleRepository.findAllById) plus an ID-only bulk status update, without binding them to the branch of the job being completed or to the set of IDs Entry originally submitted for that job; the only control is a shared service key, which the unauthenticated Engine submit endpoint effectively lends to any caller.

## 3. Bulk order status update discloses another branch's order codes in the failed-row response

Fingerprint: `OrderService:bulk-update-cross-branch-order-code`

PATCH /api/v1/orders/status (PLANNER) takes a client-supplied list of order IDs. OrderService.bulkUpdateStatus loads them with the unscoped orderRepository.findAllById, correctly refuses to transition orders whose branch differs from the caller's branch, but still copies the foreign order's orderCode into the FailedRow returned to the caller. A planner of branch A can therefore submit arbitrary (sequential Long) IDs and learn the order_code of branch B's orders, and also distinguish existing foreign IDs (non-null order_code) from nonexistent IDs (null), despite the uniform reason text 'Order not found in this branch'. No mutation of foreign orders occurs; the impact is cross-tenant disclosure of the order-code identifier plus an existence oracle.

**Claimed root cause:** The lookup is not branch-scoped (findAllById instead of a branch-bound query such as findAllByIdInAndBranchId), and the foreign-branch rejection branch populates FailedRow.orderCode from the loaded foreign entity (order != null ? order.getOrderCode() : null) instead of returning only the caller-supplied id.
